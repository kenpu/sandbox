# Task 9

This is a big redesign of `main sound listen`.

We want to design the overall system into a composition of several concurrent thread-based components:

- `ui_thread`: manages the python TUI and intercepting user interactions (keyboard), and rendering text, and playback asynchronously the audio.
- `listen`: continously collecting audio blocks, and annotating them with VAD. It is responsible at generating speech events (between VAD start and end).
- `stt`: consumes the speech events and generates text
- `tts`: consumes text blocks and generates speech synthesis

Goals (of the future):
- nonblocking despite latency in STT and TTS.
- extensible and configurable for future additions, such as LLM calls later for bi-directional conversations
- flexible UI possibilities like UI gathering low level details as well as highly processed results (like timestamped STT output, and TTS output).
- support different rendering backend: 3D graphics, web input/output

Guidelines: 

(1): I think about the data flow.  It starts with raw audio blocks collected from the sounddevice inputstream.  Data can be augmented, such as attaching the VAD event to each raw block.  Data can also be transformed entirely, like STT where the output is the text.  The design space also includes input data transformed to output data, but the eventual data is the merge of the input data and the output data.  For example, `STT: audio_block -> transcription_output` can be designed to be:
`STT: audio_block -> {"block_id": ..., "audio_duration": ..., transcription_output: ...}`
where `block_id` is from the input, and `audio_duration` is derived from the input, and the `transcription_output` is from the output.

(2): I think queues are the best way to connect components along the boundaries of concurrent components.  Queues should be minimized.  
- Compositions of nonblocking functions can be fused together, and don't need separate queues for data passing.
- A single queue might be used for hetergeneous messages, and the consumes can perform inspection message type and route them accordingly.
- Multiple producers and multiple consumes can be registered to the same queue.

This task should design the `services.*` and the CLI applications to perform the tasks with the same behaviour, but uses the concurrent component + message passing queues to function.
